@page documentation_rules 基于代码 diff 的文档更新规则

# 目标

文档审查不以“改了多少行”为准，而以 diff 是否改变读者依赖的契约为准。代码作者在提交前查看：

```bash
git diff -- CMakeLists.txt cmake package.xml src scripts config
git diff --name-only -- CMakeLists.txt cmake package.xml src scripts config
```

# 新增与归档规则（必须遵守）

新增内容先检索现有主题和引用，优先补充已有页面。确需独立页面时，先确定内容职责与所属章节，再创建文件、挂接导航；不得每完成一次任务就在工作区根目录、仓库根目录、`docs/` 根目录或网站一级目录追加一份专题文档。

1. **物理目录**：`docs/` 根目录的手写 Markdown 只保留 `index.md` 和 `architecture.md`。构建配置、布局文件和 `shell_sources.dox` 仍放在根目录；新增专题必须归入 `getting_started/`、`flows/`、`modules/`、`algorithms/`、`reference/`、`operations/` 或 `maintenance/`。完整职责见 @ref documentation_structure "文档结构与保留标准"。
2. **章节归属**：首页只挂接现有 `guide/` 章节。车型配置、一次排障或单次实验都不能成为首页/侧栏的独立一级页面。新增专题由最合适的已有章节通过唯一的 `@subpage` 收录，其他入口使用 `@ref`。新增一级章节必须对应现有章节无法容纳的一整类长期主题，并同步首页、结构约定及阅读路线。
3. **正文唯一**：每个主题只有一份正式正文。配置、脚本等目录的 README 保留文件用途和相对链接，不复制手册，也不将它们额外加入 Doxygen `INPUT`。所有被 Doxygen 读取的 Markdown 和带 `@page` 的 `.dox` 都必须参加导航检查，禁止绕过 `docs/` 的统一维护。
4. **标题规范**：`@page` 使用唯一、稳定的 ID 和纯文本标题；不得给页面标题加 Markdown 粗体或首尾空格。标题相同、只差粗体/空白的页面视为重复。例如“SANY 共用建图与定位配置”和“**SANY 共用建图与定位配置** ”属于同一主题，应合并到配置参考页，不能各占一个顶层入口。
5. **迁移同步**：整理时保留已有 page id、生成页面 URL 与有效锚点，修正仓库/工作区入口、README、脚本说明和 Doxygen 输入中的路径。原先自动生成的页面 ID 可改为显式 `@page` ID，避免移动文件后 URL 改变。
6. **证据归档**：当前诊断方法放在 `operations/`，故障记录和配套证据放在 `operations/incidents/`，图片放在 `assets/`；运行数据与批量中间产物留在 `runs/` 或外部数据目录。不得用日期、任务名或车型在顶层不断累加汇报页。

创建/迁移页面后，先跑源文件检查，再构建和检查 HTML。验收必须确认页面出现在正确章节且没有同名的第二个目录入口；仅确认文件存在或构建成功不够。

HTML 校验必须读取 `navtreedata.js` 及延迟加载的首页/章节脚本，逐页对照源文件声明的父节点；不能只检查项目根节点。文档构建统一添加导航资源的内容版本，并校验 HTML 引用与动态加载器使用同一版本，防止旧导航脚本和新页面混用。

# C++ API 文档的通用写法

API 页帮助读者快速知道“做什么、由谁调用、接下来读哪里”。算法推导、完整参数表和跨模块流程放在对应专题页，通过符号链接继续阅读。

- <b>一句话职责</b>：用 `@brief` 说明函数或类的作用。重要接口再用 1–2 句话交代调用位置、输入到输出的关系；类概述说明它负责的模块与边界。
- <b>主要流程按需写</b>：初始化、数据处理和结果发布等复杂入口用 `@par 主要流程` 列主要步骤，每步一句话，关键函数使用 `@ref`。按实际职责分段，通常为 3–7 步，不为固定数量合并独立阶段。简单转发、设置器和 getter 保持简短，指向真正执行逻辑的函数。
- <b>说明与源码分段对应</b>：函数体用 `// 阶段 N：名称。` 标出各段入口，编号、名称和执行顺序与函数头一致；阶段结束以下一阶段或函数返回为界。较长阶段只补必要的约束/原因说明，不逐行复述赋值。跨函数的类或文件概览用“调用关系”或“阅读顺序”，不能冒充某一个函数的连续执行步骤。
- <b>写清条件和执行时机</b>：早退、循环重复和条件分支直接在对应步骤说明；回调注册与回调执行、后台线程启动与 ROS Spin 调度、返回成功与结果有效应分别交代。互斥分支可以使用同一阶段下的短提示，不能让读者误以为每次调用都会走完所有步骤。
- <b>保留必要契约</b>：`@param`、`@return`、`@note` 只说明理解和正确调用所需的信息，如单位、有效性、初始化前提、异常、阻塞或退出行为；参数名必须与当前签名一致。
- <b>集中继续阅读入口</b>：用 `@see` 链接主要上下游函数或专题页，避免在每个函数里重复整个模块说明。重载有独立语义时分别说明，并使用准确的符号或签名引用。
- <b>代码示例按需展开</b>：只在关键步骤难以靠文字理解时，展示 1–2 段短代码，默认放入折叠区。用 `@snippet` 从真实源文件提取，不在注释或 Markdown 中手工复制实现。
- <b>使用稳定定位标识</b>：正文引用函数、类和 page id，不手写源码行号。Doxygen 自动生成的定义行号可保留。片段使用有语义的唯一标识，并在源文件中用普通 `// [标识]` 成对包围；每个标识恰好出现两次，重命名时同步引用。

已确认的示例：@ref lightning::LocSystem::Init() "LocSystem::Init()"。短接口参考 @ref lightning::LocSystem::SetInitPose() "SetInitPose()"；队列行为参考 @ref lightning::sys::AsyncMessageProcess "AsyncMessageProcess"。

```cpp
/**
 * @brief 一句话说明职责。
 * @details 交代调用位置与后续处理。
 * @par 主要流程
 * 1. <b>检查输入</b>：说明检查对象和早退条件。
 * 2. <b>处理数据</b>：说明本段职责，并链接关键函数。
 * 3. <b>交付结果</b>：说明交付对象和成功边界。
 * @param input 正确调用所需的输入含义。
 * @return 结果或成功、失败的含义。
 * @see 相关函数或专题页。
 */
```

对应函数体在各段入口使用 `// 阶段 1：检查输入。`、`// 阶段 2：处理数据。` 和 `// 阶段 3：交付结果。`；实际名称按函数职责确定。

模板用于组织内容，不要求每个函数写齐所有栏目。篇幅由读者需要理解的职责和约束决定，不按实现行数扩写。API 注释放在声明或定义前；函数体中的分段注释留在源码页。函数说明保留阶段名称和职责，不重复粘贴段内实现。更新后核对生成 API 页的步骤与定义链接跳转后的源码阶段，尤其检查注释是否误挂到相邻函数。

影响模块理解或正确使用的成员必须提供文档注释，包括配置与阈值、状态与有效标志、模块依赖、历史缓存与队列、线程与锁、坐标变换及诊断统计；配置和结果结构体遵循同样要求。使用声明后的 `///<` 或声明前的 `///` 写简短说明，重点交代用途、单位、坐标系、有效条件或锁的保护范围。有实际含义的普通 `//` 成员说明应改为文档注释；同一行声明多个成员时，可用 `/**< 说明 */` 分别关联，避免整行共用含混说明。

复杂约束再补充详细注释或相关符号链接，不重复类型和默认值。传感器时间戳、单调时钟、排队耗时与 CPU 耗时需明确区分；诊断样本的未测量值不能解释为零。当前配置通过 `EXTRACT_PRIVATE = YES` 展示私有成员；例如 @ref lightning::LocSystem::wheel_speed_scale_mps_per_rpm_ "轮速换算系数" 和 @ref lightning::LocSystem::trajectory_mutex_ "轨迹互斥锁"。完成后检查生成页面中的成员说明，不能只检查源码里是否出现注释。

新增片段时检查 `EXAMPLE_PATH`、文件类型、提取内容和生成页面；文件名可能重复时使用相对源码根目录的完整路径。源码注释使用 `<b>` 等 Doxygen 支持的格式，并核验实际渲染。

# 让正文中的结论可以快速核对

在线定位主线和模块页采用 @ref online_loc_code_reading "按问题核对代码" 的形式。每次选一个读者需要确认的具体问题，例如“容量 1 是否会取消正在处理的帧”，让证据就近出现：

1. 明确本段要验证的行为，以及在线/离线、配置和状态前提。
2. 用 `@snippet{lineno}` 抽取足够证明该行为的短源码。只展示函数入口通常不够；如果结论跨越配置、入队与消费，按验证顺序放出对应位置。
3. 指出应读的条件、赋值或调用，说明它为什么支持结论；变量首次出现时补充所需的单位、坐标系或有效条件。
4. 给出可手工推演的输入例子和不成立的边界。示例必须注明假设，不能冒充已经执行的测试结果。
5. 说明读到哪里已经足够，并提供下一段导读及完整 API/源码链接。仅确认调用发生，不能推断被调用函数已经成功或业务输出已发布。

不要求每节机械套用五个小标题。核心短片段在正文中直接展示，较长的初始化/退出细节使用折叠区；流程页负责交接关系，完整推演保留在所属模块，避免两处重复同一案例。源码仅添加必要的阶段/原因注释与成对标识，不为了迁就片段而改变算法或控制流。

`check_links.py` 同时检查手册和 C++ 注释中的片段：源文件必须唯一、标识必须是成对的独立注释、片段不能为空。构建后的行号/链接还需实际打开核验。正文不手写固定行号。

手写手册中的短代码块保留源码文本、语法颜色和自动行号，生成后移除块内自动符号链接，避免局部变量误连到其他文件的同名符号。继续阅读使用正文中的显式 API/源码引用；同名文件优先引用唯一的类或完整路径。完整源码页与 Shell 示例页保留其导航。验收同时检查片段文本一致、正文链接目标正确，不能只检查目标页面存在。

`prepare_html.py` 在页面顶部写入构建时的 Git 提交、相关源码/文档是否存在未提交修改，以及 UTC 生成时间，并在生成目录保存 `source_version.json`。含未提交修改时，片段来自当时的工作区，不等同于该提交的纯净源码；无 Git 信息时显示未知。它不是已部署二进制的版本证明。源码更新后必须重新构建手册；旧部署产物保留其历史版本。

# 语义触发器

即使文件路径没有新增模块，只要 diff 出现下列变化，也必须更新文档：

- 新增/删除/重命名 `add_executable`、`add_library`、install target 或 ROS dependency。
- 新增 flag、YAML key、环境变量、topic/service、输出文件或退出码。
- `unique_ptr/shared_ptr`、栈对象或回调捕获改变，导致所有权/生命周期变化。
- `std::thread/async/OpenMP`、mutex、condition variable、atomic 或队列策略变化。
- 输入排序、时间同步、坐标变换、frame ID、单位、阈值或容错变化。
- pipeline 中新增 early return、drop、fallback、重试、覆盖或删除行为。

# 结论证据规则

1. 每个关键结论至少关联“真实文件 + 符号或稳定片段标识”；优先写 Doxygen `@ref`，手写正文不使用固定源码行号。
2. API 语义必须从声明与调用者交叉确认；仅凭名称或注释不能写成事实。
3. 性能、线程安全、执行顺序若未由实现保证，前缀写 **推断：** 并说明依据。
4. 不复制大段源码；写不变量、状态转换和失败边界，并链接 API/源码。
5. 评审 diff 时验证符号和片段标识仍成立；重命名后运行 docs target 与链接检查，并检查相关 API 注释告警。
6. `index.md` → `guide/` 章节页 → 专题页使用 `@subpage` 建立唯一父节点的导航树；跨章节与专题间跳转使用 `@ref`。所有页面必须能从首页到达。双向 `@subpage` 会形成页面父子环，并可能让 Doxygen 1.9.1 长时间停在符号解析阶段；生成前先运行源文件检查。

# PR/提交检查

```text
[ ] 我检查了目标/入口/脚本/API/配置的 diff 分类。
[ ] 新增内容优先更新已有页；独立页放入职责目录并挂接已有章节，没有新增顶层专题。
[ ] 标题、正文和导航入口没有重复；迁移的 ID/URL/锚点与全仓库路径已核对。
[ ] 数据流、生命周期、线程或关键约束变化已同步到对应页。
[ ] shell 的参数、环境、cwd、调用链和副作用已同步。
[ ] 新结论有 @ref 或文件+符号证据；推断已标记。
[ ] 若涉及业务代码或依赖变化，普通构建和链接通过。
[ ] `BUILD_DOCS=ON` 的 `docs` target 通过，且 `doxygen-warnings.log` 中没有 `docs` 告警。
```

# 分层维护与校验

流程放在 `flows/`，模块职责放在 `modules/`，公式和参数化放在 `algorithms/`；`guide/` 将相关专题组织到同一个学习章节。ESKF 状态或噪声变化同时检查算法页与章节中的代码对照表；残差变更核对正负号、扰动方向、单位与信息权重。首页保持章节入口和学习路线，细节留在专题。

```bash
python3 docs/maintenance/check_links.py
cmake -S docs -B build_docs
cmake --build build_docs --target docs
python3 docs/maintenance/check_links.py --html build_docs/docs/html
```

文档构建会拒绝手写页面的 Doxygen 告警；历史源码注释告警仍留在日志，不将其误报为本轮零告警。链接检查覆盖目录归属、被 Doxygen 读取的手册页、纯文本/重复标题、唯一父节点、API 目标、锚点和图像资源；公式与图布局还需浏览器查看。

相对 Markdown 链接的目标必须纳入 Doxygen `INPUT`，仅在仓库中存在文件还不足以生成可跳转页面。`--html` 检查也会读取构建目录的 `doxygen-warnings.log`，捕获被 Doxygen 输出成普通文本的失效手册引用。

Shell 源码通过 `shell_sources.dox` 的 `@example{lineno}` 直接引用真实文件，手册用 `@ref` 跳转。新增、删除或重命名脚本时同步注册与调用说明；检查器会拒绝注册遗漏、重复或不存在的脚本。生成的脚本源码页也参加 HTML 链接检查。

源码注释变化检查非注释 token 不变。改动文档 CMake 时核验独立 docs 和 `BUILD_DOCS=ON` 两个入口；涉及业务代码或依赖变化时，再使用同一依赖环境验证业务构建。文档迁移之后检查整个仓库与工作区入口的路径，不只检查 Markdown。
