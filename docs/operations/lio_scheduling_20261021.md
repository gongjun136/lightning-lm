## 第一轮：保持两个隔离核，消除共享 LIO 工作线程依赖

SANY 启动入口现默认 `LIGHTNING_LM_LIO_THREADS=1`，全局 YAML 仍保留六线程，显式环境变量仍可覆盖。
日常启动只需 `bash ~/Sany/run_loc.sh`。三个诊断采集开关保持原有模式默认值；需要采集时才显式开启：

```bash
LIGHTNING_LM_LIO_THREADS=1 \
LIGHTNING_LM_COMPUTE_PROFILE=1 \
LIGHTNING_LM_RESOURCE_PROFILE=1 \
LIGHTNING_LM_CAUSAL_TRACE=1 \
bash ~/Sany/run_loc.sh
```

适用前提是已核验的 SANY 线程分配：CPU 10 为 `loc_sensor`，CPU 11 为
`loc_executor`/`loc_output`，后台线程为 0–9，内核已隔离 10–11。
单线程使 LIO 各 OpenMP 阶段在调用线程执行，不再依赖共享核上的五个工作线程。
18:38 静止包中匹配 P99/最大耗时为 68.40/85.89 ms，19:16 包为 65.44/78.45 ms。
这支持采用单线程默认配置，但两包仍有雷达同步或校验 UNKNOWN 引起的停车，不能标为全部故障已解决。

保持相近的感知、规划、控制负载，先静止约 15 分钟；稳定后再由现场安排相同路线的
运动、停车、起步测试。比较时记录运行版本、配置和二进制身份。
旧包可作参考，但代码变化与现场负载不同，不构成严格同输入性能对照；需要时用同一新版本分别测 1/6 线程。

定位运行中对实际 PID 执行（不可在进程退出后执行）：

```bash
python3 ~/Sany/lightning_lm_ws/src/lightning-lm/scripts/verify_localization_affinity.py PID --require-isolation
```

核对 `run_metadata.txt` 的 `lio_threads_override=1`、启动计算预算、实际线程掩码。
验收同时看 LIO scan_match/整帧 P95、P99、最大耗时，传感器队列等待、输出年龄、
实际帧率/丢弃、工作线程运行队列等待及 Safety 每次变化原因。
目标是在约 100 ms 的融合帧周期内稳定消化输入，并保持输出时效；平均值下降或 `passed=true` 均不足以验收。
如果单线程计算量超过周期而持续积压，应结束该候选并恢复既有六线程覆盖，保留失败数据。

## 单线程不足时的下一步

1. 按阶段计时优化最近邻搜索、雅可比构建、内存分配和重复计算；保持点数质量下限、残差判断和失效门限，逐项验证精度与尾延迟。
2. 若计算量确需多核，给 LIO 整个工作组配置有保证的计算核，并让接收/输出保留独立余量。
   现有两个隔离核中，CPU 11 已承担关键 I/O；简单把五个工作线程全部绑过去会引入竞争。
   如需增加第三个隔离核，先核对该域控的 CPU 拓扑、整车负载及 IRQ 路由，再确认预算变更。
3. 更大的结构调整是将高频 IMU 传播与长时 LIO 匹配解耦。当前它们共用传感器处理队列及处理锁，
   只提高线程优先级不能解除这类顺序等待。解耦需要明确状态快照、校正回注时间、重定位 epoch 和原始/平滑位姿关系，
   并做停走及延迟回归，不能仅另开一个线程共享当前滤波器。

本轮不凭空开启实时 FIFO 或更改网卡掩码，不调整 -9 条件。
CAN 可选输入和停车原始位姿修复解决的是各自有证据的故障来源，不会自动消除 LIO 和网络调度延迟。
