# SANY 雷达诊断接口与间歇性 PTP 故障（2026-10-20） {#incident_20261020_ptp}

## 现象与范围

sany-03-master 上定位和点云仍有输出，但 `/safety/throstle.runstate` 长时间或间歇性为 2。必须分别检查诊断链路兼容性、雷达当前同步状态和定位发布情况；点云频率正常不能证明时间同步正常，Safety=2 也不能直接解释为定位停发。

## 第一层：接口不兼容导致的持续故障

旧驱动发布 `/diagnostics/source_dtc/livox`，消费端订阅 `/internal/diagnostics/livox_dtc`；随后又发现从 Orin 后雷达仍使用 v1-bench，主机聚合器使用 v2-sync-source。主从消息及驱动同步部署后，话题和版本一致，持续故障解除，但仍有间歇性同步告警。

修复中增加了依赖清单、消息字段、生产者/消费者话题及运行时实际接收检查。只验证 Git SHA、编译成功或 ROS 图中存在话题均不足以验收；必须接收四路诊断、聚合 DTC、Safety 和定位消息。

## 第二层：真实 PTP 同步中断

以下时间均为北京时间，来自同一主 Orin 的日志与只读查询：

| 时间 | 原始证据与含义 |
|---|---|
| 10:26:27.114 | eth1 的 ptp4l 报 `timed out while polling for tx timestamp`、`send sync failed`，MASTER → FAULTY |
| 10:26:27.662 | Safety 变为 2，左雷达当前同步 DTC `0x11017599` 为 FAIL |
| 故障前后原始查询 | 最后同步时间停止推进，同步龄期由约 0.893 s 增至 1.393、1.893、2.393 s；HMS 新增 `0x04020002`，同期还采到 `0x04060002` |
| 10:26:43.118 | FAULTY → LISTENING |
| 10:26:50.973 | LISTENING → MASTER |

原始查询通过 SDK 读命令 0x0101，读取 0x8006、0x8009、0x800a、0x800b、0x800c、0x8011，并保存应答原文及 CRC 校验结果。该次左雷达最大绝对同步偏差约 1.965 ms。同期前、右正常。历史日志也记录了 eth2、eth3 同类发送时间戳超时，说明问题不限于左雷达。

这里不把 HMS 数字码未经厂家核验的细分含义作为唯一证据。PTP 服务实际进入 FAULTY、雷达最后同步时间冻结以及恢复后的告警消失，共同证实真实同步中断。

### 为何定位正常时仍报 2

点云继续输出不代表时间戳仍可信。`LidarDtcMonitor` 检查同步类型、同步时间推进、状态新鲜度及偏差，再由聚合器和定位安全监控转换为 Safety。现有逻辑保留当前故障，区别于历史告警；本次不删除告警、不增大新鲜度或偏差门限。

## 调度因素与验证边界

三块网卡均为 Intel igb，系统内核 5.15.148-tegra，具备硬件收发时间戳能力。故障时三个 ptp4l 均为 SCHED_OTHER，nice=0。网卡 `tx_hwtstamp_timeouts` 为 0 不能排除用户态等待超时，也不能单独证明驱动无问题。

先临时把三个 ptp4l 改为 SCHED_FIFO/20。第一轮三分钟无新 PTP 发送超时和当前 HMS 告警；并行一分钟检查收到 3001 条 Safety，全部为 0，8296 条定位消息，最大接收间隔 88.896 ms。短期改善支持调度假设，但不是根因的排他性证明。

延长实际负载验证已发现复发：10:47:15 eth1、10:48:34 eth3 再次发送时间戳超时并进入 FAULTY。10:48:51 复核三个进程仍为 FIFO/20。因此，单独提高 ptp4l 优先级没有解决故障，不能把初次三分钟正常当作修复成功。

## 部署决定与回退

**不持久化此次优先级方案，不因该方案重启服务。** 候选安装脚本已撤出交付，仅在现场取证目录保留试验材料。恢复临时试验前的进程调度策略，在主 Orin 执行：

```bash
sudo bash /home/nvidia/Sany/validation_safety_20261020/trial_ptp_priority.sh rollback
```

回退只恢复三个 ptp4l 为 SCHED_OTHER/0，不调整时钟、同步阈值或服务文件，不触发重启。需检查实际输出确认回退完成。

用户执行回退后，10:55:21 远程复查三个进程均为 TS/SCHED_OTHER，服务配置策略和优先级均为 0。没有安装持久优先级配置，没有进行候选方案的服务重启验收；原因是效果验收失败，而非修复已完成。

复发后发现三块雷达网卡的有效中断亲和性均为 CPU0，irqbalance 未运行。全机 CPU 有明显空闲，后续每核采样中 CPU0 也不是持续满载。这提示需要进一步检查中断、驱动和硬件时间戳的尾延迟，尚不能证明单核饱和或网卡硬件故障。`tx_hwtstamp_timeouts=0` 也不能否定已发生的用户态等待超时。

### 外部授时离线与启动门禁

192.168.10.50 是临时电脑：从 Orin 跟随它，主 Orin 跟随从 Orin。电脑断开后车内可继续保持相对同步，但绝对时间误差估计会增长。10:40 左右，主机 Chrony 的 root dispersion 已约 0.104 s，现有 `/usr/local/sbin/sany-ptp-guard --check` 拒绝启动。

此状态不等于当前 PTP 已停止，但直接重启可能导致服务无法重新启动。现有服务重启的 ExecStartPre 会初始化 PHC，因此应恢复合格授时后再进行，不绕过门禁、不放宽阈值。用户接回电脑后，10:43:48 从机重新选中 192.168.10.50，随后主机门禁通过；10:47、10:48 仍复发。长期离线授时架构是独立问题，不能用提高 PTP 优先级代替。授时源恢复是本次实验的条件变化，需与优先级效果分开解释。

## 诊断与停车判定分离：影子验证

车辆收到 `/safety/throstle.runstate=2` 会暂停。当前雷达 DTC 的时间同步类别并未携带完整原始偏差、同步龄期和严重级别，不能仅靠该类别 FAIL 判断是轻微偏差还是长期失同步。

2026-10-20 用户确认尚未定义允许继续运行的定位误差预算、最高作业速度和最大转弯角速度。因此本阶段明确只做影子验证：

- `RadarDtcState` 保留 `fault/all_pass` 原判定，并独立计算四路 `time_sync_fault_mask` 及除去已确认当前同步 FAIL 后的其他证据。
- 只有新鲜且明确为 FAIL 的当前同步类别进入反事实对照。UNKNOWN、过期、雷达不可用、非同步故障仍保持阻断；定位 UNKNOWN/FAIL、严重故障优先级也保持不变。
- `SAFETY_TIME_SYNC_SHADOW` 日志同时记录实际发布值、原策略值、影子值及故障角色；状态变化时记录，稳定时约每秒记录，使用现有异步日志。
- `diagnostics.radar_time_sync_shadow_enabled` 只控制审计日志，**不能关闭停车保护**。原始 DTC、聚合 DTC 和真实 `/safety/throstle` 行为不变。

例如 `published_runstate=2 strict_runstate=2 shadow_runstate=0` 只表示“这次暂停可归因于同步类别，其他已检查条件通过”。它**不表示误差已受控、不表示车辆获准继续行驶**；同样可能发生于 26 秒失同步事件。

之后若要实际放行，必须先定义误差预算及退化运行条件，再补充独立、实时的同步偏差/龄期/时间跳变证据与运动约束，验证满足边界后才修改生产停车策略。不得直接把影子值接到 Safety。

本阶段不改变 ROS 消息接口或依赖源码，`workspace.repos` 保留原锁定版本，仍执行清单和接口兼容性检查。
